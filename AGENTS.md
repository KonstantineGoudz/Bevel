# AGENTS.md

Shared context and conventions for all AI agents working in **Party Dungeon** (`/home/kon/dev/bevy`).

## Project Overview

**Party Dungeon** is a top-down 3D multiplayer party crawler and level editor built with **Bevy `0.20.0`** and **`bevy_rapier3d` `0.37`** (Rust edition `2024`, Cargo resolver `3`). It is an **MMO with one shared world and one persistent character per player**: the authoritative **physics sim runs headless at 60 Hz** (`crates/sim`, Rapier `0.36.1`), clients connect via **WebRTC data channels** using **`bevy_replicon` 0.45** over the same **`matchbox_socket 0.15`** transport (`crates/replication` schema + `crates/repl_matchbox` messaging backend; the hand-written `crates/net` snapshot/chunk path is still in-tree as the **default unbuilt path and rollback**) with **client-side prediction + reconciliation**, the **system-of-record is SurrealDB `v4.0.1`** (`crates/server`) behind a provider-agnostic **auth abstraction** (`src/auth.rs` — `AuthConfig`/`AuthProvider` for Firebase / Rauthy / any OIDC / HS256), and players sign up / log in **in-game** (Bevy UI talking to self-hosted Rauthy + a sim-hosted signup endpoint — no browser redirect, no SMTP). There are **no level files**: the sim owns the one world and **replicates it per client** — the live path uses `bevy_replicon` visibility filters for the 32 m XZ cells within `DUNGEON_WORLD_RADIUS` and the players within `DUNGEON_PLAYER_RADIUS` (the legacy path uses `ServerMsg::WorldChunk`/`WorldUnload` streaming plus per-receiver-filtered snapshots instead) — and persists player rows keyed by auth `sub`. See [docs/replicon-migration.md](docs/replicon-migration.md) for the live path and [docs/interest-management.md](docs/interest-management.md) for the legacy one. `SurrealDB` row rules and `DEFINE ACCESS` are rendered from the same `AuthConfig`.

## Repository Layout

- `game/` — Rust Cargo workspace (`members = ["crates/game", "crates/mcp-server", "crates/server", "crates/server/clients/rust", "crates/net", "crates/sim", "crates/replication", "crates/repl_matchbox"]`):
  - `game/crates/game/` (`party-dungeon`, `lib` + `cdylib` + bin):
    - `src/lib.rs` — Entry point (`#[bevy_main] pub fn main()`). Boots editor/game or `viewer::ViewerPlugin`. Re-exports `pub mod sim_support` for the headless sim (collider builder, `walking::*`, `PILL_*`, `GRAVITY`, etc.) without exposing the whole `editor` module.
    - `src/headless.rs` — Headless GPU mode (`HeadlessPlugin`, native-only): swaps winit for `ScheduleRunnerPlugin`, retargets window cameras to an offscreen `Image`, parses `--headless` / `PARTY_DUNGEON_HEADLESS*` config, and captures frames for the bridge's `/screenshot`.
    - `src/editor.rs` & `src/editor/` — Level editor (camera, selection, gizmos, transform, picking, outliner, properties, grass, hazards, movers, route, touch, bridge, world sync). `editor.rs` keeps `mod editor` private; only leafs `pub mod colliders/hazards/walking` are public, re-exported via `sim_support`. There are **no level files**: `editor/world_sync.rs` composes the client's streamed chunk store (`WorldChunks`, fed on the legacy path by `ServerMsg::WorldChunk`/`WorldUnload` and on the replicon path by `repl_client::ReplicatedWorld` mirroring replicated piece/path entities) into the in-memory world when it changes — with stable local piece ids, so the renderer updates incrementally and selection/outliner/undo/camera/grass survive a streamed update — and diffs in-game edits into `WorldOp`s for the authoritative edit path; the Maps/Save UI is gone (home is controls-only).
    - `src/auth.rs` — In-game signup/login UI + session (`AuthPlugin`, `AuthState`, `AuthSession`). Both flows hit the sim's auth API (`DUNGEON_AUTH_API_URL`): `POST /login`, `POST /refresh`, `POST /signup` — no browser redirect, and no OIDC secret in the binary. Tokens kept in memory; silent refresh. `DUNGEON_AUTH_REQUIRED=0` bypasses the gate for headless/dev (falls back to the legacy env token).
    - `src/net_client.rs` — **legacy path** (default when built without the `replicon` feature; rollback). Bevy `NetClientPlugin` (WebRTC `matchbox_socket` without `bevy_matchbox`, `Time<Fixed>::from_hz(60)`, gated on `SignedIn`: `sample_input` → `predict` (same `sim_support` maths as sim) → `send_input`, `recv_snapshots` + reconciliation (`SNAP_THRESHOLD`/`CORRECT_RATE`), a chunk store staged for incremental apply by `editor/world_sync.rs`, and `RemoteFeed` publishing the newest snapshot for `remote_players.rs`). `sample_input` samples the **camera-relative** intent the local play controller uses — `PlayerInput::move_vector()` + `Orbit.yaw` + the `Action` bindings (jump/sprint/slide), via the pure helpers `camera_relative_wish`/`input_from_controller` — and sends `Input.yaw` = camera yaw (the sim also uses that yaw as the body's facing); the old stub sent raw WASD with `yaw = 0.0`, which rotated every wish against the camera and made the authoritative body walk away from the local capsule. A one-time log records `net input: camera-relative sampling (…)` (with the sampled yaw/world direction). Known gap: touch stick/buttons feed the local controller only (via editor-private `TouchState`), so phone steering is not mirrored into net input yet — touch-driven movement is local-only and the authoritative body (and what other players see) does not follow it, while pose correction can pull it back. `net_pose_correction` (registered here) applies the authoritative local pose — see the "Authoritative sim + prediction" bullet. Token via `auth::hello_token()` (live session; the `DUNGEON_AUTH_TOKEN`/`DUNGEON_TOKEN` env fallback is used only while the auth gate is off) — see the handshake-wait bullet below for why it must never fall back mid-login. Signaling lifecycle lives here too: `NetStatus { url, state: SignalState::{Connecting,WaitingForHost,Connected,Failed,Denied}, attempt }`, a corner HUD, `retry_signaling` (5 s × 12 attempts), and `pump_signal` which uses `try_update_peers` because `update_peers` panics once the socket future is dropped. `WaitingForHost` vs `Failed` is the proxy-vs-sim diagnostic, and `WaitingForHost` **after a host peer was seen** (`NetStatus::saw_peer`) is the NAT/ICE diagnostic — three different legs, three different fixes ([docs/multiplayer-connectivity.md](docs/multiplayer-connectivity.md)). The ICE server list is read here too: `DUNGEON_ICE_SERVERS` (native) / `window.DUNGEON_ICE_SERVERS` (browser) via `party_dungeon_net::{parse_ice_servers,flatten_ice_servers}`; when it is set it replaces matchbox's built-in Google STUN defaults, and a malformed list is logged loudly and ignored. `Denied` (sim answered `Hello` with `Deny`) is surfaced on the HUD and is final for that token, but a fresh login/refresh (new token) re-arms the handshake and clears it (`hello_gate`) — see the handshake-wait bullet below. `retry_signaling` has two triggers: a scheduled retry after `Failed`, and a **stuck-handshake watchdog** (`HANDSHAKE_TIMEOUT_SECS`, 12 s) that re-joins the room when signaling is up but no host peer ever answers — a half-dead WebRTC handshake looks perfectly healthy (id assigned, no error) and used to leave the client on "waiting for the world server" forever.
    - `src/repl_client.rs` — **live path** (cargo feature `replicon`). Replaces the socket/recv path while sharing prediction, the authoritative pose correction, the editor world sync and the avatar visuals. Connects once `SignedIn` (config `{ signaling_url, token }`; token refresh replaces it → re-handshake), learns identity from `WelcomeMsg` (`ReplSession`), samples the same camera-relative intent and sends `InputMsg` every 60 Hz fixed tick, and reconciles the replicated local player entity through `editor::replicon_pose_correction` → the shared `apply_authoritative_pose`. **World:** `ReplicatedWorld`/`track_replicated_pieces` mirror replicated `PieceId`/`PieceData`/`PiecePath` entities into the *same synthetic `WorldChunks`* the legacy path feeds `editor/world_sync.rs` (deterministic cells, version bump per change, empty revision for a vanished cell), so stable ids/optimistic edits/diffs are unchanged; a replicated entity disappearing = removed from the editor world. **Edits:** staged `WorldOp`s go out as `WorldEditMsg` (≤ `MAX_WORLD_OPS`), and `EditAppliedMsg`/`EditRejectedMsg` feed the shared `PendingWorldEdits`. **Avatars:** `sync_replicated_avatars` fills `RemotePlayer`/`RemoteNameplate` from replicated `PlayerSub`/`PlayerName`/`PlayerPose` and chains `remote_players`' interpolation/nameplate systems (same `remote players:` log). **HUD/stats:** corner box from `BackendStatus` + replicon `ClientState`; `replicon stats:` once a second (`rtt` from the backend ping, KiB/s, `loss` always 0). ICE goes through `BackendIceServer` from the same `DUNGEON_ICE_SERVERS` / `window.DUNGEON_ICE_SERVERS` parsing as the legacy client. `CLIENT_BUILD` is shared by both paths.
    - `src/remote_players.rs` — Avatars for *other* players, driven off the newest snapshot via `RemoteFeed` (`self_sub` from `Welcome` + last snapshot) so it needs no socket: capsule matching the physics pill, facing wedge, per-subject colour, and a **screen-projected UI name label** (`Text` + absolute `Node`, projected from the avatar's head every frame) — not a `Text2d`, which only renders for `Camera2d` cameras and therefore never draws in this third-person `Camera3d` app. Avatars wait for `Welcome` identity (`RemoteFeed::self_sub`) before spawning (a per-receiver snapshot always contains us, so the first entry is not "self"), consume each *distinct* snapshot once gated on `(tick, self_sub, sorted remote subs)` — re-processing a packet would restart interpolation, while a changed packet with an unchanged tick must still apply — interpolate between the last two snapshots, and despawn by a **tick-based** grace (`MISSED_TICKS_MAX` = 90 ticks ≈ 1.5 s, so a slow renderer cannot stretch it). Presence logs: `remote players: N visible [subs]` (or `0 visible`) on every change, plus per-avatar `remote player visible:` / `gone:`. Unit + headless tests cover spawn, pose, interpolation, and despawn (no renderer needed). The replicon path reuses these visuals: `repl_client::sync_replicated_avatars` fills the same `RemotePlayer`/`RemoteNameplate` components from replicated `PlayerSub`/`PlayerName`/`PlayerPose` entities and chains the same interpolation/nameplate systems — only the snapshot ingest above is legacy-only.

    - `src/glade.rs`, `src/mesh.rs`, `src/gltf_export.rs` — Procedural glade/mesh and glTF export.
    - `src/controls.rs`, `src/controls_codes.rs`, `src/session.rs`, `src/viewer.rs` — Input, boot/session, model viewer.

    - `src/sim.rs` — Authoritative 60Hz tick: drain inputs, `step_movers` (Bezier, `advance_platform`), `step_player` (same `ground_step/air_step/slide_step/jump_velocity` + `PILL_*` as client), `hazards::trigger_at`, `push_dynamics`, `SimEvent` → `snapshot()`. Interact toggles bump `dungeon_version` so clients get the new `paused` flags.

Unit-tested validation.

A replicon-less binary logs a warning if `DUNGEON_REPLICON=1` and falls back to the legacy path.

## Common Commands

### Rust / Game / MCP Server (run from `game/`)

```sh
CARGO_HOME=.cargo-home cargo check --workspace
CARGO_HOME=.cargo-home cargo test --workspace
CARGO_HOME=.cargo-home cargo test -p party-dungeon-sim --lib
CARGO_HOME=.cargo-home cargo test -p party-dungeon-net --lib
cargo run -p party-dungeon          # boots empty; the world arrives from the sim after login
cargo run -p party-dungeon-mcp
# Sim headless (needs SurrealDB + Rauthy if DUNGEON_AUTH_PROVIDER != none):
DUNGEON_AUTH_PROVIDER=hs256 DUNGEON_JWT_SECRET=dev-secret cargo run -p party-dungeon-sim
```

Flags (native only) — a flag wins over its env var:

- `--headless` / `PARTY_DUNGEON_HEADLESS=1` — enable headless GPU mode.
- `--headless-size WxH` / `PARTY_DUNGEON_HEADLESS_SIZE` — offscreen viewport, default `1280x720`.
- `--headless-fps N` / `PARTY_DUNGEON_HEADLESS_FPS` — loop rate, default `60`.
- `--headless-frames N` / `PARTY_DUNGEON_HEADLESS_FRAMES` — exit after N rendered frames (bounded CI/smoke runs; default: run until quit).
- `--headless-seconds N` / `PARTY_DUNGEON_HEADLESS_SECONDS` — exit after N wall-clock seconds. Independent of `--headless-frames`; whichever is reached first wins, so a software renderer (a few fps) still finishes CI in bounded time.
- `--headless=1920x1080` — shorthand for `--headless --headless-size 1920x1080`; extra args to `./scripts/run-headless.sh` pass straight through.

`./scripts/run-headless.sh` also defaults `PARTY_DUNGEON_BRIDGE=1` and `DUNGEON_AUTH_REQUIRED=0` when they are unset. The bridge's `GET /health` additionally reports `headless`, `render {width,height,fps,frames}` and `screenshot` availability; `GET /screenshot` serves the current frame as `image/png` (the first frame right after startup can take a few seconds while the renderer warms up — the bridge waits up to 12 s), which is what the MCP `screenshot` tool fetches.


`build-web.sh` publishes one **immutable directory per build** (`web/pkg/<stamp>/…`, wasm+JS+gzipped) plus `web/pkg/build.json`, the tiny manifest that names the live stamp. The pages fetch that manifest with `no-store` and load `pkg/<stamp>/…`, so a reload transfers only revalidations and only a new build fetches a new wasm — the stamp is generated by the script and compiled into the wasm (`CLIENT_BUILD`) automatically, no hand-kept pair. Compression is precomputed (`gzip -9`, wasm ~11.7 MB release vs ~49.8 MB raw). Full design, verification commands, rollback and knobs: [docs/web-caching.md](docs/web-caching.md).

**Both ends must be built with the same feature selection** (the replicon handshake compares the protocol hash): sim image `DUNGEON_SIM_FEATURES=replicon` at build time + `DUNGEON_REPLICON=1` at runtime via `./up.sh --build`, and the web client with `--features replicon`. Those are compose interpolation values in `game/.env`; rollback = rebuild both with the feature off / `DUNGEON_REPLICON=0`. Full cutover/rollback commands: [docs/replicon-migration.md](docs/replicon-migration.md).

Production hosting (`play.conman.biz`): the static site (`index.html` / `game.html` / `pkg` / `assets`) is served from this host by a durable `nginx:alpine` container, **not** `serve-web.py`:

```sh
# `./scripts/deploy-web.sh` does exactly this (it validates the config first):
docker run -d --name party-dungeon-web \
  -p 6082:80 \
  -v /home/kon/dev/bevy/game/web:/usr/share/nginx/html:ro \
  -v /home/kon/dev/bevy/game/web/nginx.conf:/etc/nginx/conf.d/default.conf:ro \
  --restart unless-stopped nginx:alpine
```

- Why: `serve-web.py` is a dev process; when it died with a host interruption the public site returned 502 while `/login` and `/party-dungeon` kept working (those proxy straight to the sim and never touch the static site). The container survives host/session interruptions.
- Public front: NPM on `192.168.0.172` forwards `play.conman.biz/` → `192.168.0.143:6082` (this web container), `/login|/signup|/refresh` → `:6565` (sim auth API), and `/party-dungeon` → `:6536` (matchbox signaling; keep the path — it is the room id). NPM's admin API login is `{"identity": …, "secret": …}`.
- **Do not drop the `nginx.conf` mount.** It carries the cache policy (`pkg/<stamp>/` immutable, `pkg/build.json` `no-store`, HTML/`assets/` revalidated, `gzip_static`); without it nginx serves the stock default and the browser re-downloads the wasm on most loads. `./scripts/deploy-web.sh` re-creates the container with the mount.
- The data mount is read-only and nginx serves from disk, so a `./scripts/build-web.sh` on this host is live without restarting the container (restart only when nginx config/locations change). If you build elsewhere, copy `game/web/{pkg,assets,*.html}` into the mounted directory. Files must be world-readable (mode `644`) or the unprivileged nginx workers answer **403** — a `write`-tool-created file is `0600`, which broke `viewer-bevy.html` once.
- Build stamp (automatic): `./scripts/build-web.sh` generates a UTC stamp (`PARTY_DUNGEON_BUILD` overrides), writes it to `web/pkg/build.json` (and into each build's own `web/pkg/<stamp>/build.json`) and compiles the same value into `crates/game/src/net_client.rs`'s `CLIENT_BUILD` via `crates/game/build.rs`; native/dev builds report `dev`. The HUD prints `CLIENT_BUILD` in every connection message, so a screenshot proves which build is actually deployed. There is no constant to keep in sync — the live stamp is whatever `curl https://play.conman.biz/pkg/build.json` reports; rollback is copying an older build's manifest over `pkg/build.json` (see [docs/web-caching.md](docs/web-caching.md)).

## Key Conventions & Gotchas

- **Do not hand-edit `game/web/assets/` or `game/web/pkg/`**: `./scripts/build-web.sh` replaces `web/assets/` from `game/assets/`, regenerates `web/assets/models.json` for `viewer-bevy.html`, and publishes `web/pkg/<stamp>/` + `web/pkg/build.json` (pruning to `PARTY_DUNGEON_KEEP_BUILDS`, default 2; the previous build stays as the rollback target). Served files must be world-readable (`644`) — the nginx workers are unprivileged, and `write`/`edit`-tool-created files are `0600` (that returned 403 for `viewer-bevy.html`).
- **Cargo profiles**: `dev` and `wasm-dev` use `opt-level = 1` so Bevy runs at interactive framerates without slow full-LTO builds; use `release` / `wasm-release` only for final builds.
- **glTF textures**: `bevy` in `game/crates/game/Cargo.toml` explicitly enables the `jpeg` feature because Bevy 0.20 omits it by default and glTF allows JPEG textures.
- **Single shared world, no level files**: the sim owns the one world and replicates it to each client. **Live path (`replicon`)**: `crates/replication` visibility filters — world geometry cells within `DUNGEON_WORLD_RADIUS` (default 128 m) and other players within `DUNGEON_PLAYER_RADIUS` (default 96 m), both server-env only — mirrored client-side by `repl_client::ReplicatedWorld` into the same synthetic `WorldChunks` → `editor/world_sync.rs`; see [docs/replicon-migration.md](docs/replicon-migration.md). **Legacy path (default unbuilt / rollback)**: 32 m XZ cells around the character (`ServerMsg::WorldChunk`/`WorldUnload`, per-peer chunk budget) plus per-receiver-filtered `Snapshot`s, applied by the same `world_sync`; see [docs/interest-management.md](docs/interest-management.md). On the legacy path a native client with the MCP live bridge on (default for native) or `DUNGEON_FULL_WORLD=1` requests the whole world (`ClientMsg::SetInterest` with `None` radii) so `/state` and the MCP tools converge on complete geometry (it still streams at the per-peer chunk budget, so a vast world takes seconds to drain); WASM clients always stream, and a native client streams when `PARTY_DUNGEON_BRIDGE=0`. **On the replicon path `SetInterest` is not honoured** — radii are server env — so an MCP-bridge native client sees only `DUNGEON_WORLD_RADIUS` and `/state` is a partial world (prefer the DB source for edits/imports). `game/levels/demo.json` is only the one-time seed (import it once via `import_snapshot`). The home screen has no Maps tab; the editor boots empty and fills in from replication after login. Editor-only cosmetics (trigger colors/visibility, non-glade trigger opacity, outliner names/groups/locks, grass) are session-local and never persisted — the DB carries gameplay data only; a streamed re-apply rebuilds pieces from the wire, so per-piece trigger cosmetics reset while outliner metadata survives for pieces that stay resident. **Glade roof pitch is the exception**: it is gameplay, stored in the `trigger_alpha` slot and persisted/replicated (see the roof-pitch bullet). Both edit paths are authoritative and meet in the same world: MCP/DB edits are picked up by the sim's DB poll, and **in-game edits are sent as `ClientMsg::WorldEdit` (legacy) or `WorldEditMsg` (replicon) and persisted by the sim** (client-detected ops → service-role reducers → changed cells re-replicated) — see the next bullet.
- **Authoritative world edits from the game (in-game edits are not MCP-only)**: `editor/world_sync.rs::sync_edits` diffs the editor against what the streamed store last showed and stages `WorldOp`s: a new local piece → `Place { tag, piece }`, changed gameplay fields on a persisted piece → `Update { piece }` (throttled per rid, ~0.15 s, so a gizmo drag cannot flood the reliable channel), a user deletion → `Delete { rid }` (a delete is optimistic as well: the piece is hidden locally until the store echo no longer contains it, and a rejection reinstalls it) — while a piece that merely left the interest radius is forgotten silently (an unload is not a deletion). `net_client` (legacy) sends them as `ClientMsg::WorldEdit { ops }` and `repl_client` (replicon) as `WorldEditMsg { ops }` — both ≤ `MAX_WORLD_OPS` = 64 per message, kept queued until the reliable channel accepts. The sim validates them (`sim/src/world_edit.rs`: the same value rules as the store plus the shape catalogue this build can instantiate), persists them through the service-role reducers `create_piece`/`update_piece`/`delete_piece` (system of record; dev mode with no DB mints `dungeon_piece:local-N`), applies them to the authoritative world, and bumps `dungeon_version` **once per batch** (`Sim::rebuild_current`) so only the changed cells re-stream/replicate — an emptied cell is tombstoned and cleared. `ServerMsg::WorldEditApplied { tag, rid }` (legacy) / `EditAppliedMsg { tag, rid }` (replicon) map the client's optimistic tag to the store-generated rid *before* the echo arrives (so the streamed chunk/replicated piece updates in place instead of duplicating it); `ServerMsg::WorldEditRejected { key, reason }` / `EditRejectedMsg` drop/roll back the optimistic copy and log a warning. The client keeps the optimistic piece visible until the echo/rejection arrives, and pending overrides win over streamed values until the store echoes a canonical change. Mover-path authoring is not part of this protocol — tracks still go through the `set_platform_path` reducer / MCP.
- **Glade roof pitch is shared gameplay, carried in `trigger_alpha`**: a glade piece's roof pitch is `glade::roof_pitch(piece, shape)` = `sanitize_trigger_alpha(piece.trigger_alpha) * 2.0` (roof-bearing kinds; it returns `0.0` for wall/stairs/door/window/terrain/tree); `Piece.trigger_alpha` is always the raw `0..1` value (`TRIGGER_DEFAULT_ALPHA` 0.35). It is persisted and replicated: `WorldPiece.trigger_alpha` (`party-dungeon-net`) is gameplay for glade shapes and editor-local trigger opacity otherwise; on the replicon wire it is `PieceData.trigger_alpha` (`u16` over 0..1); `party_dungeon_server::{Piece, NewPiece}` carry it; `dungeon_piece.trigger_alpha` is `TYPE float` with the `0..=1` rule in the schema template (fresh installs), and `create_piece`/`update_piece` apply `Transform::SanitizeAlpha` with `clients/rust` regenerated. The sim carries it through `world_edit`/`stream`/`piece_from_wire` (legacy) and `repl/convert.rs` (replicon), and `Backend::validated_piece` clamps instead of rejecting (so old clients and stored snapshots always write a valid row). **Live-DB migration** (applied): SurrealDB 4 refuses a NONE-rejecting `TYPE float` on a table that already has rows, so the live field was defined as `DEFINE FIELD trigger_alpha ON dungeon_piece TYPE option<float>` with a backfill of `0.35`; the table-level permission rule was not re-applied live, so runtime clamping (`Backend::validated_piece`, the generated client's transform, and the sim's `world_edit` validation of `0..=1`) is the guard there. Editor round-trip: `SavedPiece.trigger_alpha` holds the **roof pitch** for glade shapes (the `SavedPiece` unit is the pitch, matching `capture`/`SavedPiece::from_piece`), and `session.rs`'s loader divides it by 2 into `Piece.trigger_alpha`; `editor/world_sync.rs` stores `Some(roof_pitch)` for glade, compares glade alpha in gameplay equality, so a roof-pitch edit sends exactly one `Update` (and the streamed echo clears the override). Non-glade trigger opacity stays editor-local (not streamed/persisted).
- **Headless GPU mode is the real renderer without a window (how the game is driven without a browser)**: `--headless` / `PARTY_DUNGEON_HEADLESS=1` disables `WinitPlugin` and runs `ScheduleRunnerPlugin` instead, so no window, event loop, or display server is ever created — but the full wgpu renderer still initializes (PBR, UI, glTF, the grass compute pipeline) and draws into an offscreen `Image` render target. Every camera whose target is a window (main + minimap) is retargeted to that image once, in `PostStartup` (`headless::retarget_cameras`). The auth overlay is suppressed (headless has no keyboard to log in with) and `DUNGEON_AUTH_REQUIRED` defaults to `0` — an explicit env value still wins. The live MCP bridge (default `127.0.0.1:6559`) keeps working unchanged; under `--headless` its `GET /health` also reports `headless`, `render {width,height,fps,frames}` and `screenshot` availability, and `GET /screenshot` serves PNG frames of the offscreen target (what the MCP `screenshot` tool fetches). Screenshots are armed only after the renderer has drawn a frame, so the first request after startup can take a few seconds on a software renderer (the bridge waits up to 12 s); a failing target never blocks the game. Use `--headless-frames N` and/or `--headless-seconds N` for bounded CI/smoke runs (whichever is reached first ends the run) — `./scripts/check-headless.sh` does exactly that and asserts a clean exit.
- **In-game auth (no browser, no SMTP, no secret in the binary)**: `game/src/auth.rs` (`AuthPlugin`) shows a login/signup overlay until `AuthState::SignedIn`. Both flows go to the **sim's auth API** (`DUNGEON_AUTH_API_URL`, default the play origin): `POST /login` and `POST /refresh` proxy the OIDC password/refresh grants with `RAUTHY_CLIENT_SECRET`, and `POST /signup` creates the Rauthy user via the admin API (`RAUTHY_API_KEY`). The client therefore never holds a secret, so a **confidential** Rauthy client is fine (a public client would also work). Tokens live in memory; silent refresh happens automatically. `DUNGEON_AUTH_REQUIRED=0` bypasses the gate for headless/dev (falls back to the legacy env token). The form's four rows are hand-rolled (`AuthFieldKind`/`AuthFieldValue`, one keyboard handler) rather than Bevy's `TextInput`, because that widget is only focusable via `TabIndex` — see the click-to-focus gotcha below. On touch devices the same rows also get native `<input>` overlays, because a canvas can never summon a phone keyboard — see the mobile soft-keyboard gotcha below. The sim persists one character per auth `sub` on Hello (`connect_player`, plus `register_player` when the client sends the signup name). Config differs per deployment, and browsers have no env vars, so **`game/web/game.html` injects it before boot**: `window.DUNGEON_SIGNAL_URL`, `window.DUNGEON_AUTH_API_URL` and `window.DUNGEON_ICE_SERVERS` (read via `lib.rs::web_global`; `?signal=…`, `?auth=…`, `?ice=…` override all three for debugging). Same-origin in production (`/party-dungeon` + `/login` … on the play host); on `localhost`/`127.0.0.1` the page points straight at the sim (`ws://localhost:6536/party-dungeon`, `http://localhost:6565`) because `serve-web.py` is a static server, not a WebSocket/auth proxy. The replicon path sends the same `AuthSession` token in its matchbox handshake (`Hello { token, protocol }`) and re-handshakes when the token refreshes (`repl_client::sync_backend_token`).
- **The handshake must wait one frame for `AuthSession` (the Android "Malformed token: expected header.payload.signature" login bug)**: `auth::poll_auth_inbox` sets `AuthState::SignedIn` synchronously but inserts `AuthSession` through deferred `Commands`, so one frame can run signed-in with the resource still invisible. `handle_signaling` used to read the token then and fall back to `dev-anon`, which the sim rejects as a malformed JWT — and `Denied` was sticky (`hello_sent` stayed true), so re-logging in did not recover. Both handshakes now gate on `auth::hello_token(session)` and wait while it is `None` (`net_client::handle_signaling`, `repl_client::insert_backend_config`); the legacy client keeps `NetClient::sent_token` and `hello_gate` re-arms (clearing `Denied`) when a fresh login/refresh yields a new token. The log `net hello: source=session|env … parts=3` (3 parts = JWT, 1 = dev fallback, will be denied; `… deferring the handshake a frame` when it waited) is the fingerprint. `auth::{hello_token,live_token,token_shape}` and `hello_gate` are unit-tested.
- **`.env` gotchas (these cost real time)**: compose interpolates `$` inside `env_file` values, and **Rauthy API keys are `name$secret`** — write them as `RAUTHY_API_KEY=name$$secret` (the sim normalizes `$$`→`$`). Never re-declare such secrets in a compose `environment:` block via `${...}`; let `env_file` pass them through. `game/.env` (used for compose interpolation) and `crates/server/.env` (read by the tools) must stay in sync — `game/up.sh` and the bootstrap script assume it.
- **Bevy ECS conflicts are runtime panics, not compile errors (this class of bug shipped twice)**: `error[B0001]` = a system's params access the same component mutably in two queries Bevy cannot prove disjoint (`With<A>` vs `With<B>` is *not* disjoint — an entity may have both); `error[B0002]` = the same resource as both `Res` and `ResMut` in one system. Neither is caught by `cargo check`/`clippy`, only when the system first runs — i.e. in the browser, mid-session. Two rules:
  - Prefer one query with a small tag component (`AuthSection`/`AuthTextKind` in `auth.rs`, `NetStatusBox`/`NetStatusLabel`) over several marker-filtered `Query<&mut Node>`/`Query<&mut Text>`; where markers stay, every pair needs an explicit `Without`.
  - Every new plugin gets a headless boot test that runs `app.update()` a couple of times (`auth::tests`, `editor/tests/boot.rs`), so a bad param pair fails `cargo test`, not a user's login.
- **Click-to-focus needs `TabIndex` (why the login form ignored every keystroke)**: `bevy_input_focus::PointerFocusPlugin` resolves a click by focusing the target **only if it carries `TabIndex`**; otherwise the `AcquireFocus` request bubbles to the window and *clears* focus. A `TextInput`/`EditableText` row without `TabIndex` therefore can never be clicked into, and typing goes nowhere — silently, with no error. The auth panel now hand-rolls its four rows (`AuthFieldKind` + `AuthFieldValue` + `Button` + `TabIndex`) with one keyboard handler: chars, Backspace/Delete, Enter = submit, Escape = clear error, Tab = next *visible* row (login hides name/invite), plus a caret in the focused row. Editor property fields already carry `TabIndex`; anything new that takes typing needs one too.
- **Seeing other players**: there is no global roster broadcast — each client only learns about players near it. **Live path (replicon):** other players replicate as `PlayerSub`/`PlayerName`/`PlayerPose` entities gated by `PlayerCell` vs the client's `VisiblePlayerCells` set (radius `DUNGEON_PLAYER_RADIUS`, default 96 m, sim env); `repl_client::sync_replicated_avatars` turns them into the same avatars and logs `remote players: N visible [subs]`. **Legacy path:** each `Snapshot` carries only the players within the receiver's player radius (`DEFAULT_PLAYER_RADIUS` = 96 m, its `SetInterest`, or everyone for a full-world dev client), always including the receiver itself; `remote_players.rs` turns the ones that are not us into avatars. So "I don't see them" is first a **distance/interest** question: a player beyond 96 m (or with the cell geometry not yet replicated) is invisible by design. If two people "join" but see nothing, check in this order: (1) both clients actually connected and standing within the player radius — a connected client logs `remote player visible: <name>`; (2) the HUD corner message distinguishes the legs: `Failed` = the signaling/proxy route, `WaitingForHost` = the sim is not in the room (legacy additionally distinguishes red `WaitingForHost` after a host peer was seen (`NetStatus::saw_peer`) = the direct WebRTC link failed; the replicon HUD is `BackendStatus`-driven with `WaitingForHost`/`Handshaking`/`Failed`/`Connected` and logs `relayed=`, see [docs/replicon-migration.md](docs/replicon-migration.md)); on the legacy path the watchdog re-joins every 12 s up to 12 attempts, which cannot fix NAT by itself; (3) `cargo run -p party-dungeon-sim --example signal_probe` proves the host is reachable from a machine in under a second, independent of a browser (both paths: it joins the room, not the replicon handshake); (4) `SELECT name, online FROM player` in SurrealDB shows whether each client ever completed a handshake/`Hello`. A `player.online` of `false` after a session means the peer dropped, not that the avatar is broken.
- **WebRTC connectivity / TURN (why a phone on mobile data cannot reach the sim)**: connecting has three independent legs — the signaling WebSocket (`wss://…/party-dungeon` via NPM, TCP 443), the peer-to-peer WebRTC data channel (direct/STUN; blocked by carrier-grade NAT and strict firewalls), and a TURN relay fallback. Signaling can be perfectly healthy while the data channel never completes, so the corner HUD distinguishes them: `Failed` = signaling/proxy route, grey `WaitingForHost` = the sim is not in the room, red `WaitingForHost` after a host peer was seen (`saw_peer`) = the direct link failed (mobile data/strict NAT — try Wi-Fi or TURN). The replicon path uses the **same** signaling room, NPM routes and ICE/TURN list; its HUD is `BackendStatus`-driven (`WaitingForHost`/`Handshaking`/`Failed`/`Connected`, `relayed=` logged) and has no `saw_peer` NAT message, so a NAT failure shows up as a long `WaitingForHost`/`Failed` — see [docs/replicon-migration.md](docs/replicon-migration.md). Configure the same JSON relay list on every end: `DUNGEON_ICE_SERVERS` on the sim and the native client, `window.DUNGEON_ICE_SERVERS` in `game/web/game.html` (must be a JSON **string**; `?ice=` overrides for debugging), browser `RTCIceServer` shape `[{urls,username,credential}]`, one credential pair per deployment. Setting it **replaces** matchbox's built-in Google STUN defaults, so include the STUN URLs you want; a malformed list is logged loudly and ignored (STUN-only fallback). TURN needs a relay host (self-hosted coturn with UDP 3478 + relay range forwarded, or a hosted provider) and both the sim image and the web build must be rebuilt/redeployed after changing it. Debug with `./scripts/check-signal.sh` (leg 1), `cargo run -p party-dungeon-sim --example signal_probe -- wss://play.conman.biz/party-dungeon` (legs 1+2 from a given network), `chrome://webrtc-internals`, and the client log `webrtc link up: local=… remote=… relayed=true/false`. Full recipe, coturn compose snippet, and incident checklist: [docs/multiplayer-connectivity.md](docs/multiplayer-connectivity.md).
- **Mobile soft keyboard needs a native `<input>` (why the login fields did nothing on phones)**: winit's web backend attaches `keydown` to the `<canvas>`, and a canvas is not an editable element — so tapping a Bevy-drawn field can never summon the OS keyboard, and keys typed into a real `<input>` never reach the canvas either (the events never bubble through it). Both text-entry surfaces therefore mirror a real DOM input: the editor's `#bevy-text-input` (`editor/add_menu.rs::WasmTextBridge`), and the auth form's four overlays `#bevy-auth-email` / `-name` / `-invite` / `-password` (`auth.rs::KeyboardBridge`). The auth overlays are created once on wasm, positioned every frame from `ComputedNode` + `UiGlobalTransform` (physical px around the node **centre** → CSS px from the top-left) over the corresponding rows, and their `input`/`keydown`/`focus` events are drained from a mutex mailbox into `AuthFieldValue`/`InputFocus` (Enter on the password row = submit, Enter/Tab on earlier rows = next *visible* row, matching the desktop handler). The bridge arms itself only on touch — `navigator.maxTouchPoints > 0` at startup, or the first `Touches` event — and is a no-op on desktop/native, which keeps the normal Bevy keyboard path. A new typing surface needs these overlays *on top of* `TabIndex`, and `web-sys` needs the `DomRect` (bounding rects) + `KeyboardEvent` features for it.
- **Auth API CORS is dev-only**: `/signup`, `/login`, `/refresh` add CORS headers via `signup.rs::dev_cors` **only for loopback origins** (`http://localhost…`, `http://127.0.0.1…`, `http://[::1]…`). Production is same-origin behind NPM, so it needs none of this; it exists because `serve-web.py` (:6082) and the sim's auth API (:6565) are different origins locally, and without it the browser reports "Failed to fetch" for every login. Changing it requires rebuilding the sim image; the game client never does.
- **Bevy asset `.meta` requests**: `AssetMetaCheck` defaults to `Always`, so the browser fetches `<asset>.meta` beside every asset (`/assets/character.glb.meta 404`). Nothing here ships meta files, so `AssetPlugin { meta_check: AssetMetaCheck::Never, .. }` in `src/lib.rs` kills that noise and one round trip per asset. If asset processing is ever adopted, revisit this.
- **Password policy is Rauthy's**: 8+ chars with at least one upper, lower, digit and special character. It is enforced in three places that must agree: the in-game form (`auth.rs`), the sim (`signup.rs::validate_signup`), and Rauthy itself. Rejecting before user creation matters — a mid-provisioning failure would strand a password-less account, so the sim deletes the user if the password step fails.

- **Auth is provider-agnostic — never hard-code Firebase/Auth0/Rauthy outside `crates/server/src/auth.rs`:**
  - `AuthProvider::{Firebase,Rauthy,Oidc,Hs256,None}` + `AuthConfig::from_env()` reads `DUNGEON_AUTH_PROVIDER` and `DUNGEON_*` (`DUNGEON_FIREBASE_PROJECT_ID`, `DUNGEON_RAUTHY_URL/ISSUER/AUDIENCE/JWKS_URL`, `DUNGEON_OIDC_ISSUER/AUDIENCE/JWKS_URL`, `DUNGEON_JWT_SECRET`, …). Inference fallback: `DUNGEON_FIREBASE_PROJECT_ID` → `firebase`, `DUNGEON_RAUTHY_URL` → `rauthy`, `DUNGEON_OIDC_ISSUER` → `oidc`, `DUNGEON_JWT_SECRET` → `hs256`.
  - `AuthClaims { iss: Option<String>, aud: Option<AudValue(String|Vec)>, sub, ns/db/ac }` — `aud` can be a single string *or* array (Auth0 does both). `decode_claims_unverified` is display/routing only; SurrealDB re-verifies via JWKS on every statement.
  - `SurrealConfig { auth: AuthConfig, firebase_project_id }` keeps the deprecated field for `struct` literal compat but `auth` is the source of truth; `SurrealConfig::from_env()` derives both.
  - `schema.surql` is a **template** (`__AUTH_ACCESS_DEFINITION__`, `__AUTH_ROW_PREDICATE__`, `__AUTH_OWNERSHIP_PREDICATE__`), rendered at bootstrap via `AuthConfig::render_schema`. `DEFINE ACCESS` and every `PERMISSIONS … WHERE` are derived from the same `AuthConfig` — a token from another tenant verifies its signature but matches no rows.
  - Routing claims `{ns,db,ac}` must be stamped via the IdP's hook: Firebase `setCustomUserClaims`, Rauthy/Auth0 Action, etc. (`scripts/firebase-claims.mjs` is the Firebase example; other providers use their own hook).
  - Client token env is `DUNGEON_AUTH_TOKEN` → `DUNGEON_TOKEN` → `DUNGEON_FIREBASE_TOKEN` → `dev-anon` (all read in `crates/game/src/net_client.rs::auth_token()`). Swapping providers is `DUNGEON_AUTH_PROVIDER` + 2–3 vars + `bootstrap.sh` — no code change.
- **Rauthy self-hosted is the local default:** `crates/server/.env.example` ships `DUNGEON_AUTH_PROVIDER=rauthy` + `DUNGEON_RAUTHY_URL=http://localhost:6080`, `ISSUER=http://localhost:6080/auth/v1`, `AUDIENCE=party-dungeon`, `JWKS_URL=http://rauthy:6080/auth/v1/oidc/jwks` (internal). `docker-compose.yml` runs `ghcr.io/sebadob/rauthy:0.30.0` with hiqlite (`rauthy-data` volume, `rauthy.cfg` + `PUB_URL`/`ENC_KEYS` from `.env`). SurrealDB fetches JWKS at `http://rauthy:6080/...` while row rules check `iss == 'http://localhost:6080/auth/v1'` (both hosts are correct — JWKS host is internal, `iss` host is what the browser sees).
- **Reducer registry is the single source of truth:** `crates/server/src/reducers.rs` defines every `ReducerDef`/`QueryDef` once (params, SurrealQL, `transactional`, `checks`, `probe`, `client_callable`, `transforms`). `crates/server/src/backend.rs` (service role, full validation) and `crates/server/src/codegen.rs` → `crates/server/clients/rust` (player package, byte-identical SurrealQL, row rules are the only delta) both consume it. `transforms` canonicalize (`Trim`, `NormalizeDeg`, `SanitizeExtent`, `CanonicalInteract`) so both sides send the same values. `gen_schema` renders the schema from the same `AuthConfig`.
- **Authoritative sim + prediction:** `crates/sim` owns one Rapier world built from the *game's own* `sim_support::piece_collider_for_glade` + `platforms::build_platform_track`, so art can never desync collision. Players are kinematic state integrated by hand (never solver bodies) via shared `sim_support::{ground_step,air_step,slide_step,jump_velocity}` and `PILL_*`/`GRAVITY`. The Bevy client (`crates/game/src/net_client.rs`, `NetClientPlugin`, `Time::<Fixed>::from_hz(60)`) samples `Input` at 60 Hz, predicts locally with the same helpers, and reconciles on `Snapshot` (`SNAP_THRESHOLD`/`CORRECT_RATE`); remotes interpolate `INTERP_DELAY_TICKS` behind. **The local body follows the authoritative pose** via `net_pose_correction` (`NetClientPlugin`, ordered `.after(NetReconciliation)` / `.after(editor::PlayController)` / `.before(editor::CameraFollow)`): `editor::apply_authoritative_pose` pulls `Editor::character` toward the newest snapshot's self state — pos/feet/velocity blended at `CORRECT_RATE`, snapped past `SNAP_THRESHOLD`, exact yaw, authoritative `hp`/`max_hp`/`alive`, rising-jump `vy` protected — and delta-follows the third-person camera target so the camera moves with the body. It is inert without `NetClient`, while signed out, unless the link is `Connected`, and when the newest snapshot is stale or lacks our `sub`; it only acts in `Mode::Play` with no route walk, so authoring modes and route walking keep their purely local body. A snapped correction logs `local pose corrected by X.XX m` at most once per second. `Input.yaw` doubles as body yaw, so third-person facing follows the camera (matching what remotes see); touch input is not mirrored into net input yet (the phone body is not driven by the sim, and pose correction can pull local touch movement back). Wire is `matchbox_socket 0.15` (no `bevy_matchbox` — it pins Bevy 0.19) with `matchbox_signaling` `ClientServer` topology: first peer is host (sim), channel 0 reliable (`ClientMsg`/`ServerMsg`), channel 1 unreliable (`Snapshot`). The replicon client **reuses all of this**: `repl_client` samples the same camera-relative intent into `InputMsg`, advances the shared `Predicted`, and feeds the replicated local player entity through `editor::replicon_pose_correction` → the same `apply_authoritative_pose` (blend/snap/hp/jump/camera-follow); only the transport differs (channel 0 handshake, replicon channels after).
- **Replication (`bevy_replicon`) path — live**: `bevy_replicon 0.45` over the existing matchbox/WebRTC transport (`crates/repl_matchbox` messaging backend, same `/party-dungeon` room + TURN; `crates/replication` schema — binary postcard, no JSON/protobuf, quantized `PieceData`/`PlayerPose`/`PiecePath` + `PlayerSub`/`PlayerName`; visibility filters `WorldCell`+`VisibleCells` for geometry and `PlayerCell`+`VisiblePlayerCells` for players; client messages `InputMsg` (unreliable, 60 Hz) / `WorldEditMsg` (ordered, ≤ 64 ops), server messages `WelcomeMsg`/`EditAppliedMsg`/`EditRejectedMsg`/`NoticeMsg`). The handshake rides reliable matchbox channel 0 — `Hello { token, protocol }` → `Welcome { sub, name, tick }`/`Deny`, JWT decoded exactly like the legacy `Hello`, and a protocol-hash mismatch is a hard `Deny` — while replicon channel `i` maps to matchbox channel `i + 1` (stronger reliability wins). Selection: cargo feature `replicon` on `party-dungeon` + `party-dungeon-sim`, sim runtime `DUNGEON_REPLICON=1` (+ compose `DUNGEON_SIM_FEATURES` build arg), web `./scripts/build-web.sh --features replicon` / `PARTY_DUNGEON_FEATURES`; default-off = legacy path. **Both ends must be rebuilt together** (protocol hash); rollback = rebuild both without the feature / `DUNGEON_REPLICON=0`. Interest is replicon visibility only: `DUNGEON_WORLD_RADIUS` (128 m) / `DUNGEON_PLAYER_RADIUS` (96 m) are sim env, `SetInterest` is not honoured on this path (the MCP full-world caveat above). Stats: client `ClientStats` (rtt from the control ping, bps) logged as `replicon stats: rtt … ms, loss 0.00%, sent … KiB/s, recv … KiB/s` once a second; server per-client `ConnectedClientStats` has bps only (matchbox/SCTP exposes no RTT/loss). Known gaps: mover-path *authoring* is not in `WorldEditMsg` (tracks replicate/animate via `PiecePath`; dragging waypoints is still MCP/reducer-only), touch steering is still local-only, visibility removal and delete are both "removed from the world" client-side, and `piece.damage` is quantized to whole store points. Full architecture/contract/cutover/verification: [docs/replicon-migration.md](docs/replicon-migration.md); the legacy path docs remain valid for the unbuilt/rollback build.
